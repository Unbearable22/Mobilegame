# Chain React v0.6: deterministic mechanics contract

Status: implementation proposal prepared from the v0.6 request and the current `ReactionEngine`, `GridManager`, validator and auditor. This document specifies behavior; its existence does not mean that any new mechanic has shipped or passed tests. The first implementation slice is Reflector, Portal, AND Gate and Delay. Toggle, Filter, Inverter, Lock, Amplifier and Temporal remain specification only. The decisions below are engineering/design proposals within the requested autonomous scope, rather than claims of separate user approval.

## Compatibility boundary

The seven existing types retain their exact rules. Existing level JSON, node order, source indices, rotation actions, launch budgets, target persistence and saved completion IDs 1–50 stay valid. Rotation is permitted only before the first accepted launch, including for new rotatable types. A launch must finish before another player action is accepted. Active visual state persists between launches but does **not** prevent activation/emission in a later launch. Only a launch-local consumed set prevents repeated emission in the same launch.

| Existing type | Input and output that must remain unchanged |
|---|---|
| `source` | Only the selected source starts at tick 0; emit its rotated `dirs`. Incoming hits to any source are absorbed. |
| `normal` | First eligible incoming batch activates it and emits in all four directions. |
| `directional` | First eligible batch activates it and emits its one rotated direction. Input direction never gates entry. |
| `splitter` | First eligible batch activates it and emits each of its rotated configured directions. |
| `blocker` | Absorb every arrival; never activate or emit. |
| `battery` | Before its first emission in the launch, add the **number of incoming edge events** to persistent charge, capped at 2. Charge below 2 does not activate or consume it. At charge 2 activate and emit all four directions once. Charge persists across ticks and launches. A battery already at 2 emits on its first new hit in each later launch. |
| `target` | First eligible batch activates it, emits nothing; activation persists. Win requires at least one target and all targets active. |

Orthogonal edges connect only immediately adjacent occupied cells; empty cells do not transmit rays. Out-of-board/missing destinations produce no arrival. Node array index is its stable simulation identity. Rotation uses `(base_direction + rotations[index]) % 4` and does not alter node coordinates. No new handler can mutate the input level or the caller's `before` state.

Legacy regression evidence must compare final state and legacy frame nodes/edges/state for all 50 levels, not merely victory. With no new types, the event implementation must yield the same waves, simultaneous battery counting, empty activation lists, and traversal edge order as the old implementation. Existing `dirs` ordering stays intact for legacy edges; do not globally sort that stored array. Additional optional event metadata does not change those values.

## Chosen architecture and alternatives

Use a pure discrete tick scheduler inside `ReactionEngine`, with separate validated node handlers. This extends the existing wave model and makes arrival grouping and delays explicit. A scene-tree timer solution couples rules to frame rate and cannot serve a deterministic offline solver. Repeated scanning of the whole board can model short delays but obscures termination and same-tick input grouping. Neither alternative is selected.

The engine owns queue order, grouping, budgets, state copies and trace frames. A handler receives the immutable node definition, the complete incoming batch for one tick, a tick-start state snapshot and launch context. It proposes state changes and emissions; it never advances time or recursively calls another handler. The scheduler commits proposals in the phases below. Keep validation, simulation, presentation and offline proof generation separate.

### Directions, signals and events

Directions are **travelling directions**, not the side from which a tile was entered: `0=up`, `1=right`, `2=down`, `3=left`. An edge from the cell left of a tile has incoming direction 1. For adjacent cells, derive direction from `position[to] - position[from]`; never infer it from source orientation. An event is:

```text
arrival = {tick, from, to, direction, signal_type:"A", strength:1, sequence}
release = {tick, node, outputs, signal_type:"A", strength:1, sequence}
```

`sequence` is a monotonically increasing launch-local integer assigned during enqueue, beginning at 0. Distinct incoming neighbors means distinct `from` indices, not directions, signal counts or historical charges. Virtual portal transport is a display-only edge `{from:entry,to:partner,kind:"portal",direction:-1}` in the tick frame, never a queued ordinary arrival. Exclude it from adjacency/direction validation of real arrivals, handler input grouping, battery charge and AND distinct-neighbor counting. This explicit kind prevents recursive teleportation; real orthogonal arrivals always have direction 0–3.

For the first four mechanics every real arrival is the legacy default signal A, strength 1. Accepting future typed-signal JSON now would expose unimplemented behavior: reject future-only configuration in the v0.6 content validator. The future signal contract reserves `signal_type` in `{A,B}` and integer `strength` in `[1,4]`; these values are bounded design limits, with gameplay balance to be playtested. At future typed-signal activation, all simultaneous-input handlers that need one representative select minimum `(signal_type A before B, -strength, from, direction, sequence)`. This is a fixed rule, not arrival-order luck. Emitters then preserve that representative except where their mechanic explicitly transforms it. A battery still counts events, never strength; when it finally emits, its representative comes from that tick, not historical charge. Source defaults to A/1 and may gain an explicit typed source field only in that future schema. Target accepts either type/strength. Once typed signals ship, test their interaction with all seven legacy nodes.

### Tick phases and stable ordering

1. Initialize a deep working copy, empty queue, empty node-consumed set and empty portal-pair-consumed set. Set the selected source active and consumed. Tick 0 records its activation and schedules its ordinary adjacent arrivals for tick 1.
2. At tick `t`, detach **all** queued arrivals and release events due at `t`. Freeze the tick-start state. Group arrivals by target index. Process targets in ascending index. Preserve arrival insertion order for trace compatibility; use the canonical representative rule above for any selection. Pair activation is computed across both portal endpoints before either endpoint is processed, so simultaneous endpoint inputs are symmetric.
3. Evaluate every handler on its entire batch. Commit activations, battery changes, future toggle changes and permitted emissions together. A node that has already consumed its activation in this launch absorbs later arrivals. A failed condition (AND missing a second neighbor, a future filter mismatch, closed lock or temporal mismatch) does not consume the node.
4. Ordinary emission at `t` creates adjacent arrivals at `t+1`. A delay schedules a release, as specified below. A release due at `t` emits at `t`, so its adjacent arrivals also join tick `t+1`. Nothing newly emitted can create another ordinary activation at `t`.
5. Apply future lock unlocks after all node activations for `t`; these become usable at `t+1`. Record one immutable frame after tick effects. Continue until both arrivals and releases are empty.

Simultaneous arrivals at one legacy battery must all be counted before deciding whether it emits. Processing a node early must never erase a second hit from that tick. Portal pair reservation groups both endpoints in the same first-use tick; it cannot depend on target iteration order.

### Trace frames and animation

The existing result shape remains `{accepted, state, frames, won}`; new rejected simulations add a stable `error` code. The source frame remains `frames[0]`. For an accepted launch, retain **one frame for every integer tick from 0 through the last arrival/release**, including empty waiting ticks. Preserve existing `nodes`, `edges`, `state`; optional `tick`, `released`, `transports`, `waiting` and signal metadata can support the renderer. `nodes` lists activations in ascending index (source is the sole tick-0 activation). `edges` shows arrivals occurring in that tick. A target reached by a delay must not visually receive an edge early. A delay's release is visible through its release marker/countdown; its outgoing arrival edges appear in the next frame. A portal transport is a nonorthogonal display edge marked `kind:"portal",direction:-1`; never process it as an ordinary arrival. Display edges may be included in `edges` for renderer compatibility, with real arrivals retaining their own direction and `kind` absent or `"orthogonal"`. Place transport edges after real arrival edges in stable entry-index order.

Waiting frames still contain a deep state snapshot and empty arrays as appropriate. Playback speed, pause, reduced effects and screen refresh rate change presentation only. They cannot remove a tick from engine data or change AND/Temporal timing. A completed launch with no remaining events adds no trailing empty frames. A delay with no occupied configured exit does not enqueue a useless release.

### Termination, failure and transactions

All eleven v0.6 types (the seven existing types plus four new types) consume at most once per node per launch. A reflector may route multiple directions in its **one** activation batch; it does not activate again. A portal pair has one activation transaction per launch and consumes both endpoints together; each endpoint transports at most once in that transaction. A waiting delay is already consumed. Feedback edges can still be shown arriving at consumed nodes, but they generate no more output. Future six types inherit the same bound.

Hard safety limits are ticks `0..127` inclusive (128 frames maximum) and 4096 queued events per launch, counting every arrival and every scheduled release once at enqueue; each display-only portal transport also counts once when staged (at most two per pair). Count processed/absorbed arrivals too. Check before scheduling tick 128 or event 4097. These are implementation safety bounds, not difficulty claims. Validated campaign content must finish strictly inside them.

On any budget overflow or runtime invariant failure return `{accepted:false, state:before.deep_copy, frames:[], won:has_won(before), error:"reaction_tick_limit"|"reaction_event_limit"|"invalid_reaction"}`. Discard all staged active/charge/toggle/unlock changes. `GridManager` must then add no history entry, consume no launch, increment no gameplay statistics and award no completion. Presentation can display a recoverable level error. Never return `accepted:true` after truncating an event queue; that would silently produce an incorrect puzzle result. Invalid source selection is also rejected without mutation. Validation rejects malformed pairs/configuration before play.

## First implementation slice

### 1. Reflector — `reflector`

**Purpose:** make a corner depend on entry direction, rather than behave as a fixed arrow. **Input:** any real adjacent arrival on an unconsumed reflector; no port rejects an entry. **Output:** reflect each incoming direction using the table, union duplicate outgoing directions, then emit one edge per occupied outgoing neighbor at `t+1`. Sort these new output directions ascending for deterministic traces. A mirror tile is a routing rule, not a ray that continues through empty cells.

| Travelling in | Even rotation: `/` | Odd rotation: `\` |
|---:|---:|---:|
| 0 up | 1 right | 3 left |
| 1 right | 0 up | 2 down |
| 2 down | 3 left | 1 right |
| 3 left | 2 down | 0 up |

Its base surface is always `/`; rotation parity chooses the surface. Rotation 0 and 2 have identical behavior, as do 1 and 3. A tap still advances the shared rotation counter by one quarter turn, so two taps restore the surface. Do not add `dirs`, a second mirror orientation field, entry masks or diagonal travel.

**State:** existing `active[index]` and `rotations[index]` only. One eligible batch activates even when every reflected exit is empty. **Between launches:** active and rotation persist; no incoming-direction memory persists. **Simultaneous inputs:** all directions in the first eligible batch contribute; later tick arrivals are absorbed. With future typed signals, choose one canonical representative per output direction among events mapped there. **Cycles:** one activation batch per launch. **Undo/Restart:** restore the exact prior active/rotation arrays; restart returns them to false/0. **Visual:** unambiguous slash/backslash stroke and visible entry-to-exit pulse; rotation affordance only when `rotatable:true`. Theme colors cannot be the sole orientation indicator.

**JSON:** common `x,y,type`; optional Boolean `rotatable` defaults false. Disallow `dirs`, `pair_id`, `delay_ticks`. Example: `{"x":2,"y":2,"type":"reflector","rotatable":true}`. Initial rotation remains 0 as for all current nodes; authored JSON does not add a hidden initial state.

### 2. Portal — `portal`

**Purpose:** connect distant local circuits without changing the orthogonal neighbor rule. **Definition:** exactly two distinct portal nodes share a `pair_id` matching `^[A-Za-z0-9_-]{1,32}$` (ASCII letters, digits, underscore or hyphen; length 1–32). Each endpoint has its own nonempty unique `dirs` in `[0,3]`, describing the shape of that endpoint **when used as the exit**. Portals are fixed in this slice (`rotatable` absent/false); authors explicitly choose each endpoint's exit directions.

**Input:** any real adjacent arrival to either endpoint, regardless of direction. At the earliest tick containing any arrival to the unused pair, gather the batches for **both** endpoints before resolving the pair. Each endpoint with a nonempty batch acts as an entry once; select its canonical representative if that batch contains several inputs. **Output:** activate/consume both nodes immediately at `t`. For each entry, record one display transport to its partner, and emit only the **partner's** configured `dirs` from the partner's cell; adjacent arrivals occur at `t+1`. With input at just one endpoint, only its partner emits. With simultaneous input at both endpoints, both transport once and both endpoints emit their own exit shapes once. This is one pair activation transaction, not recursive transport. The teleport has zero extra tick cost beyond its normal outgoing neighbor hop.

**State:** existing active array only; pair identity/exit shape are immutable level configuration. Pair reservation and entry set are launch-local. **Between launches:** active remains visible; the pair becomes eligible again. **Simultaneous inputs:** multiple hits to one endpoint do not duplicate its transport or partner output. Hits at both endpoints in the first tick are resolved symmetrically; never choose a winner by node index. With future typed signals, each entry sends its own canonical representative to the other endpoint's exits. **Cycles:** partner activation and display transport are not ordinary portal arrivals. Do not recursively teleport back or enqueue a portal-to-portal arrival. A real later arrival at either endpoint is absorbed because the pair is consumed. Separate pairs can form a finite multi-pair route.

**Undo/Restart:** restore both activations atomically; no pair-use state survives a completed/undone launch. **Visual:** matching pair labels plus matching shape/pattern, exit arrows on each endpoint, transport pulse; pair identity remains readable without color. Both endpoints show active status after use. **JSON:** `{"x":1,"y":2,"type":"portal","pair_id":"p1","dirs":[0,1]}` plus exactly one partner with `pair_id:"p1"`. Reject IDs outside the allowlist/length, IDs with other than two endpoints, duplicate/empty exit lists, self-pairing, and `rotatable:true`. `dirs` is required with 1–4 entries at both endpoints; there is no default implicit exit shape. No implicit pairing by proximity or display color.

### 3. AND Gate — `and_gate`

**Purpose:** require same-tick convergence instead of stored battery charge. **Input condition:** the unconsumed gate's current tick batch contains arrivals from at least two **distinct adjacent source-node indices**. Two events from one neighbor do not qualify. No exact input-side restriction is implied. **Output:** on success activate and emit its nonempty rotated `dirs`, with adjacent arrivals at `t+1`. Three or four distinct incoming neighbors still cause one activation/emission batch.

**State:** existing active/rotation arrays only. Pending inputs are discarded at the end of the tick. **Between launches:** visual active persists, but successful history never substitutes for a current second input; no charge or latched-input state exists. **Simultaneous inputs:** evaluate the complete group before deciding. Failed tick 2 plus failed tick 3 do not combine. Failed inputs from separate launches do not combine. Under future typed signals, A and B both count as incoming neighbors; output uses the canonical representative, not a new combined type. **Cycles:** failed ticks may be retried within a launch; the first successful tick consumes the node and later arrivals are absorbed. **Undo/Restart:** active/rotation restore; no transient half-input survives. **Visual:** `&` with two independently blinking input pips for the current tick, configured exit arrows and a full flash only on success; never reuse battery charge bars.

**JSON:** common fields plus nonempty unique `dirs`; optional Boolean `rotatable` defaults false. Example: `{"x":3,"y":2,"type":"and_gate","dirs":[0],"rotatable":true}`. Gate threshold is fixed at two; reject configurable threshold and persistent charge fields in this slice.

### 4. Delay — `delay`

**Purpose:** align two otherwise different path lengths while preserving a visible logical timeline. **Input:** first eligible adjacent batch. **Output:** activate/consume at arrival tick `t`; schedule one release at `t + delay_ticks`; release emits its nonempty rotated `dirs`. Neighbor arrivals therefore occur at `t + delay_ticks + 1`. Example: input tick 2, delay 1, release tick 3, neighbor arrival tick 4. An ordinary relay receiving tick 2 would reach the neighbor at tick 3; delay 1 adds exactly one tick.

**State:** existing active/rotation arrays only. Pending release and captured signal/exit list are launch-local. Capture rotated exits when activated, although player rotation is already disallowed during launches. **Between launches:** there is no pending work; a launch cannot end while a release remains. Each later launch can schedule a fresh release. **Simultaneous inputs:** one release using canonical representative; do not add durations, schedule one per hit, restart the timer or multiply output strength. **Cycles:** consumed on scheduling, so a feedback hit cannot reset/release it again. **Undo/Restart:** a completed launch snapshot restores active state; all work is already drained. If presentation is cancelled/restarted while animating, discard playback and all transient display countdowns; engine results do not depend on animation callbacks. **Visual:** clock symbol, permanent 1/2/3 numeral, discrete waiting countdown with a release flash, exit arrows. Reduced effects retains numeral/countdown information.

**JSON:** common fields plus nonempty unique `dirs`, required integer `delay_ticks` in `[1,3]`, optional Boolean `rotatable` defaults false. Example: `{"x":2,"y":3,"type":"delay","dirs":[1],"delay_ticks":2}`. Reject 0, fractions, negative numbers and values above 3.

## Future mechanics: specification only

Do not add these six types to v0.6 playable content, current guide availability, achievements or generator output. Their schema fields are reserved and rejected until a later schema explicitly enables them. They use the same adjacency, batching, once-per-launch activation, typed representative rule, tick caps and transactional rollback. The following state fields are **future** node-indexed arrays in a versioned board snapshot; they must not be introduced into the first-four state implementation merely to reserve names.

### 5. Toggle — `toggle`

**Purpose:** alternate routes across launches. **Configuration:** `dirs_0` and `dirs_1`, each a nonempty unique direction list; `initial_toggle` integer 0 or 1 defaults 0; optional `rotatable` false. Reject equal direction sets because they hide the mechanic. **State:** persistent `toggle_modes[index]`, initialized from `initial_toggle`; existing active and rotation also apply. **Input/output:** first eligible batch at `t` emits from the current mode's rotated exit list using the canonical signal, then flips mode exactly once at end of `t`. The newly displayed mode controls the **next launch**, not the output already emitted. **Simultaneous:** one batch/one flip, independent of hit count. **Cycles:** later hits in that launch are absorbed and cannot flip again. **Between launches:** mode and active persist. **Undo:** restores the previous mode, active and rotations together; **Restart:** restores configured initial mode, false active and zero rotations. **Visual:** labeled 0/1 state, distinct two-route glyphs and next-mode marker; flash the route actually used before displaying the new mode. **Serialization:** future JSON fields as above; snapshot includes exact integer mode. Reject Boolean/fractional mode, missing route list and unknown mode. No automatic timed toggling.

### 6. Filter — `filter`

**Purpose:** route a chosen signal kind, with an optional strength condition for Amplifier puzzles. **Configuration:** `accept_type` required A or B; `min_strength` integer `[1,4]` defaults 1; nonempty unique `dirs`; optional `rotatable` false. **Input:** eligible events satisfy both type equality and strength at least the minimum. **Output:** if any event qualifies, activate once and emit the canonical representative among **qualifying events only** through rotated exits without modifying type/strength. Nonmatching events are absorbed and do not consume the node, so a later qualifying tick may still activate it. **State:** active/rotation only; no accepted-type mutation or stored input. **Simultaneous:** mismatching events cannot veto matching events or contribute strength. **Cycles:** first qualifying batch consumes; no later output in the same launch. **Between launches:** configuration remains fixed; active persists. **Undo/Restart:** common snapshot/initial-state rules. **Visual:** A/B label plus pattern, strength bars/numeral when minimum exceeds 1, visible reject/accept pulse. **Serialization:** snapshot needs no additional persistent keys; invalid type/minimum/exit lists reject the level.

### 7. Inverter — `inverter`

**Purpose:** change A to B and B to A predictably. **Configuration:** nonempty unique `dirs`, optional `rotatable` false. No custom mapping field or strength negation. **Input:** any first eligible batch. **Output:** choose canonical input, swap A/B, preserve strength, emit through rotated exits. **State:** active/rotation only. **Simultaneous:** one representative and one inversion, never cancellation of A plus B. **Cycles:** consumes once, so a loop cannot alternate a node repeatedly. **Between launches:** no retained signal type; active persists. **Undo/Restart:** common rules. **Visual:** explicit A↔B symbol, incoming/outgoing label change; no reliance on hue alone. **Serialization:** only common fields/dirs; typed-signal schema must be enabled before the node is valid.

### 8. Lock — `lock`

**Purpose:** make a key activation open a later route. **Configuration:** `key_index` identifies exactly one other stable node in the same level; it may be any activatable type, including a source/target, but not a blocker or itself. Nonempty unique `dirs`; optional `rotatable` false. Do not infer the key from adjacency or introduce an eleventh new key-node type. **State:** persistent Boolean `unlocked[index]`, initially false, plus common active/rotation. **Input/output:** an arrival passes only when unlocked at **tick start**; then activate/consume and emit canonical signal through rotated exits. Locked hits are absorbed with no storage and no consumption. **Opening:** after each tick, if its key is active, set unlocked true; never relock. Keys already active before the launch also open the lock before tick-0 processing. If a key activates at tick `t`, the lock can pass arrivals at `t+1`, but same-tick arrivals remain blocked. Key-source activation at tick 0 therefore opens in time for ordinary tick-1 arrivals. Unlocking alone neither activates the lock nor emits a pulse. **Simultaneous:** key and arrival at the same tick follow the same tick-start rule regardless of indices. **Cycles:** an unlocked lock can activate once; mutual key dependencies can be unsolvable and must fail solver validation. **Between launches:** unlocked and key active persist. **Undo:** restores both key activation and lock Boolean, never derive unlocked from a later state; **Restart:** resets both and applies no hidden key activation. **Visual:** labeled key-link badge, closed/open padlock glyph, exit arrows; open and activated are separate indicators. **Serialization:** future snapshot must include Boolean `unlocked`; level validates key range/type. Do not mutate or remove the node to represent opening.

### 9. Amplifier — `amplifier`

**Purpose:** satisfy a future Filter strength threshold without multiplying event count. **Configuration:** integer `gain` in `[1,3]`, nonempty unique `dirs`, optional `rotatable` false. **Input/output:** first eligible batch selects canonical input and emits that type with `min(4, input.strength + gain)` through rotated exits. It does not clone pulses, add simultaneous strengths or add battery charge. **State:** active/rotation only; no energy stockpile. **Simultaneous:** choose one strongest canonical representative under the common type-first rule; many weak hits do not merge. **Cycles:** once per launch and saturation at 4 both bound growth; a feedback hit cannot increment it again. **Between launches:** no strength persists. **Undo/Restart:** common rules. **Visual:** `+gain` badge and bounded four-segment output meter; never show uncapped growth. **Serialization:** required gain/dirs, no persistent amplifier field. Reject gain 0, >3 or fractional.

### 10. Temporal Node — `temporal`

**Purpose:** require an arrival at one specified launch-relative tick. **Configuration:** integer `activation_tick` in `[1,127]`, nonempty unique `dirs`, optional `rotatable` false. **Input:** at least one arrival at exactly `activation_tick`; arrivals before/after are absorbed, not queued. **Output:** activate/consume at that tick, emit canonical input through rotated exits with adjacent arrivals one tick later. A legal tick-127 activation with occupied exits would exceed the cap and rejects the launch; campaign validation must exclude this construction rather than silently drop output. **State:** active/rotation only; launch-local tick is not persistent time. **Simultaneous:** canonical representative from the qualifying tick. **Cycles:** first qualifying activation consumes; incorrect earlier arrivals do not. **Between launches:** the clock resets to tick 0; previous launches and real-world time never count. **Undo/Restart:** common rules and reset playback clock; no wall-clock timestamps serialized. **Visual:** clock plus `t=N`, readable current launch tick and rejection feedback; use a distinct face from Delay's `+N` indicator. **Serialization:** required activation_tick/dirs, no future deadline/real-time field. No autonomous activation merely because the tick is reached: an input is still required.

## State, serialization and integration

First-four board snapshots stay `{rotations:Array[int], charges:Array[int], active:Array[bool]}` with array lengths equal to node count. Rotation integers are 0–3; charges 0–2; active entries Boolean. Deep-copy on every frame and history entry. Node configuration belongs to level JSON; mutable state belongs to the board snapshot; queues, consumed sets and countdowns belong only to a launch. No pending-event save/resume is introduced. Player progress saves remain completion/statistics/settings data, not half-executed engine queues.

New campaign levels should declare an explicit level `schema_version:2`; missing version continues to mean the original format. Reject unsupported higher versions, unknown new types, invalid direction lists, noninteger coordinates/durations and pair/cardinality failures with actionable validator messages. New keys must not reinterpret legacy definitions. A board snapshot format version is required before enabling future `toggle_modes`/`unlocked` arrays; migration initializes those from immutable level configuration and does not add them to unrelated legacy saves. Existing campaign save migration is described in [v6-campaign-plan.md](v6-campaign-plan.md).

`GridManager.launch` remains the sole transaction boundary: accepted results snapshot/commit/increment once; rejected ones do none. Undo of a launch restores state and launch count; Undo of a rotation restores rotation. Restart reloads immutable definitions, resets arrays/counters and clears history. Restart/Undo during playback must cancel visual callbacks before rendering the restored snapshot. A stale release animation must never write into engine state. Statistics must distinguish an accepted user launch from an internal release/portal event.

The guide defines direction, same-tick grouping and Delay tick arithmetic before combination levels. Glyphs/labels must be consistent in tiles, guide, hints and trace tests. New visuals require 720×1280, 1080×1920 and 1440×3200 screenshots in normal/reduced effects and at least two themes. Mouse screenshots cannot establish physical Android touch/back correctness.

## Solver and proof contract

Keep solver output deterministic and explicitly bounded. Return one of `solved`, `unsolved_complete`, `budget_exceeded`, `invalid`; a timeout/limit is never proof of no solution. Use ascending node indices/source indices, fixed rotation order, stable state serialization and operation-count budgets instead of machine-time dependent acceptance. Reuse the exact gameplay engine, including rejected launches, same-tick rules and delay frames.

The legal action grammar is zero or more rotations **before the first launch**, followed by source launches up to the level budget; Undo and Restart are editing aids, not proof actions. Do not change rotations between launches while searching. Search state includes rotations, charges, active, launches used and any future persistent toggle/unlocked arrays; queue state is absent because each launch drains completely. Canonical mirror orientations may reduce a solver's search space to parity, but replay must retain real tap counts when reporting action minima. Distinguish minimum launches, minimum changed nodes and minimum rotation taps; the current orientation enumeration does not prove minimum taps.

Proposal: maximum 200,000 canonical search states and 500,000 launch simulations per level audit, plus the per-launch event/tick caps above. If either proof budget is hit, report incomplete and withhold the candidate from playable content. A found witness establishes solvability and attainable rating, but it does not establish optimality or absence of bypasses if enumeration was incomplete. Authoring may simplify the board or use a stronger offline proof budget recorded in its artifact; runtime must not silently raise budgets. All numerical difficulty estimates remain design hypotheses until playtesting; engine caps and schema ranges are intentional fixed rules.

## Required automated examples before enabling content

- Legacy: replay all current author traces, compare legacy wave fixtures, two hits in one tick, different-tick battery accumulation, multi-launch battery/target persistence, sources absorbing inputs, feedback loops, and full Undo/Restart restoration.
- Reflector: all eight table mappings, rotation parity, no empty-cell rays, two simultaneous inputs yielding two outputs, duplicate output coalescing, and a later return edge absorbed.
- Portal: entry from each end uses the other's exits; both active; far partner animation; simultaneous endpoint hits emit both endpoint exit sets once; duplicate hits to one endpoint still transport once; three malformed pairing cases; separate pairs in a route; pair loop terminates; no recursive partner transport; next launch reuses pair; exact Undo.
- AND: two distinct neighbors same tick succeed; portal display transport never counts as a neighbor; one neighbor duplicated fails; two ticks fail; two launches fail; three neighbors cause one emission; failed early tick then later valid tick succeeds; battery success is not confused with gate success.
- Delay: d=1/2/3 exact release/neighbor tick arithmetic; empty frames; overlapping releases join one batch; simultaneous hits schedule once; feedback never resets delay; no stale countdown after Undo/Restart; a delayed route aligns AND while unadjusted route fails.
- Limits: event 4096 and tick 127 boundary behavior; one event/tick over rejects with byte-equivalent prior state, unchanged launch/history/statistics, no partial frames or victory. Invalid input state/configuration rejects predictably.
- Determinism: repeat identical inputs and compare full serialized results; vary frame rate/playback speed without changing any engine trace. New handler tests must assert exact ticks and interactions, not victory alone.
